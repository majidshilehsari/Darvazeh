# رابط جدید و سهمیهٔ دستگاه‌ها — 0.3.0-preview.1

## رابط

- هدر با تب‌های واقعی نمای کلی، دستگاه‌ها، دستگاه‌های متصل، تاریخچه و تنظیمات اتصال؛ تب متصل بر اساس اتصال‌های باز است، نه صرفاً فعال‌بودن اعتبار.
- مودال داخلی برای افزودن/ویرایش دستگاه، عملیات فعال/غیرفعال/تعویض کلید، تنظیمات هسته، restart، پروفایل کلاینت، ثبت آزمایش، پاک‌سازی و صادرات تاریخچه و خروج. `alert/confirm/prompt` مرورگر استفاده نمی‌شود.
- پیام‌های موفقیت، خطا و پیشرفت در جای ثابتِ چیدمان زیر هدر؛ پیام خطا خودکار محو نمی‌شود. خطای مودال نیز در همان مودال دیده می‌شود.
- جدول هم‌تراز، جست‌وجوی نام، منوی عملیات، چراغ رنگی همراه متن، نوار سهمیه با عدد مصرف/باقی‌مانده. نامحدود نوار پرشدگی جعلی ندارد. رنگ به‌تنهایی حامل معنا نیست.
- موبایل: جدول در محفظهٔ خود افقی اسکرول می‌شود و صفحه overflow ندارد؛ مودال از عرض صفحه بیرون نمی‌زند. دسترسی صفحه‌کلید، Escape، برگشت فوکوس و تب‌های ARIA در نظر گرفته شده‌اند.

## سهمیه دقیقاً چگونه عمل می‌کند؟

- سقف حجم در UI با **GB ده‌دهی** است: هر GB = 1,000,000,000 بایت؛ مجموع ارسال + دریافت. مقدار صفر یعنی نامحدود.
- اعتبار روزهای تقویمی از **اولین اتصال ثبت‌شدهٔ دستگاه** است، نه مجموع ساعت آنلاین. صفر یعنی بدون انقضا. برای دستگاه تازه قبل از اتصال، تاریخ پایان ساخته نمی‌شود.
- پیش‌فرض مودال دستگاه جدید **۵ GB و ۱۰ روز** است و پیش از ذخیره قابل ویرایش است. دستگاه‌های قدیمی به‌صورت خودکار محدود نمی‌شوند؛ در نبود فیلد محدودیت، صفر/نامحدود در نظر گرفته می‌شود.
- ویرایش سقف/مدت، فعال‌کردن مجدد یا تعویض UUID مصرف و زمان شروع را صفر نمی‌کند. پایین‌آوردن سقف از مصرف فعلی یا کوتاه‌کردن مدت می‌تواند بلافاصله دستگاه را مسدود کند. تمدید مدت نسبت به همان اولین مشاهده محاسبه می‌شود.
- UI وضعیت‌های متصل (سبز)، بدون اتصال (خاکستری)، منقضی (کهربایی)، غیرفعال/سهمیه تمام‌شده (قرمز)، پایش ناموجود (هشدار) را جدا نمایش می‌دهد.

### شمارندهٔ پایدار و قطع واقعی

`usage` در SQLite مستقل از جدول `connections` است. پاک‌سازی ۷روزه یا دکمهٔ حذف تاریخچه به مصرف سهمیه دست نمی‌زند. نرخ استفاده از همهٔ اتصال‌های هم‌زمان یک دستگاه به‌صورت سریال و اتمیک از یک مانده کسر می‌شود.

بایت‌ها **پیش از ارسال از واسط به مقصد بعدی رزرو و در DB ثبت می‌شوند**؛ شامل سربار فریم WS هستند، نه حجم خالص فایل، شمارندهٔ ISP یا اثبات تحویل داده. این انتخاب مانع برگشت سهمیه با crash می‌شود؛ اگر فرایند بین ثبت و ارسال متوقف شود، ممکن است بایت رزروشده‌ای که تحویل نشده هم مصرف حساب شود. اندازهٔ read عادی تا 64KiB است؛ بافر آغاز احراز می‌تواند از یک read بزرگ‌تر باشد. شروع HTTP/TLS ورودی جزو این شمارنده نیست.

در تمام‌شدن حجم، ادامهٔ انتقال و اتصال‌های دیگر همان دستگاه بسته می‌شوند؛ دستگاه دیگر قطع نمی‌شود. انقضا روی هر درخواست مصرف و تقریباً هر ثانیه برای اتصال بیکار بررسی می‌شود. با خطای دیتابیس شمارنده، دستگاه محدود **fail-closed** می‌شود؛ مصرف نامحدودِ بدون نظارت جایگزین نمی‌شود.

این راهکار یک ledger تراکنشی کوچک روی Volume است و هر قطعهٔ انتقال می‌تواند نوشتن DB ایجاد کند. ظرفیت/سرعت روی Hostim بنچمارک نشده است؛ برای گروه کوچک طراحی شده، نه تضمین تعداد اتصال یا throughput مشخص.

### جلوگیری از مسیرهای دورزدن محدودیت

- دادهٔ معمول WS قبل از عبور محتوای VLESS باید به UUID فعال منتسب شود؛ prefix نامعتبر یا ناشناخته ارسال نمی‌شود. بافر و زمان اولیه محدود است.
- اگر حتی یک دستگاه دارای سقف/مدت باشد، **Early Data با `Sec-WebSocket-Protocol` روی این ورودی رد می‌شود** تا انتساب‌ناپذیری آن راه فرار از سهمیه نباشد. لینک‌های صادرشدهٔ پنل Early Data ندارند. کاربران پروفایل دستی دارای `?ed=...` باید آن را حذف کنند. این تغییر در محیط دارای دستگاه محدود ممکن است روی دستگاه نامحدودی که Early Data دارد هم اثر بگذارد.
- `MONITOR_ENABLED=0`: فقط دستگاه‌های نامحدود در کانفیگ Xray قرار می‌گیرند. دستگاه محدود با خاموش‌شدن پایش به نامحدود تبدیل نمی‌شود. API هم تعیین سهمیهٔ جدید در این حالت را رد می‌کند.
- اگر DB در راه‌اندازی آماده نباشد، دستگاه‌های محدود از ورودی هسته کنار گذاشته می‌شوند. API لینک برای دستگاه منقضی، سهمیه‌تمام‌شده یا بدون شمارندهٔ سالم صادر نمی‌کند.
- کسی که لینک نامحدود دیگری را در اختیار دارد می‌تواند از آن اعتبار استفاده کند؛ این طرح تشخیص فیزیکی دستگاه یا جلوگیری از اشتراک‌گذاری کلید نیست.

## مهاجرت و حفاظت داده

- نسخهٔ DB از ۱ به **۲** افزایش می‌یابد؛ جدول‌های قبلی حذف نمی‌شوند.
- پیش از migration، snapshot یک‌بارنویس `history-before-quota-v2.sqlite3` گرفته می‌شود. این snapshot ممکن است IP داشته باشد و مشمول حذف پس از ۷ روز است.
- مصرف اولیه و اولین مشاهدهٔ دستگاه قدیمی فقط از **تاریخچهٔ باقی‌مانده** استخراج می‌شود. سوابق حذف‌شدهٔ قبلی قابل بازیابی نیستند. در UI برچسب `مبنای اولیه: تاریخچهٔ باقی‌مانده` نمایش داده می‌شود. شمارنده از این نسخه به بعد مستقل و ماندگار است.
- migration با INSERT OR IGNORE انجام می‌شود و دوباره‌اجراشدن، مصرف را دوباره جمع نمی‌کند. schema ناشناخته یا دادهٔ خراب خودکار بازسازی نمی‌شود.
- بکاپ تنظیمات افزایشی در `/data/backups/settings-before-0.3.0.json` قرار می‌گیرد؛ فایل قبلی بازنویسی نمی‌شود. بکاپ‌های نسخه‌های قدیمی حذف نمی‌شوند. UUID اصلی حفظ می‌شود.
- فقط **یک replica** روی این Volume مجاز است. snapshot بیرونی باید با ابزارهای مناسب SQLite/WAL یا توقف کنترل‌شده انجام شود؛ کپی صرف فایل اصلی DB فعال بدون WAL تضمین سازگاری نمی‌دهد.

## تنظیمات کلاینت و Fragment / Mux

مودال پروفایل کلاینت یک خروجی **Xray-core JSON خصوصی** می‌سازد؛ نه تنظیم خودکار گوشی و نه لینک اشتراکی که همهٔ کلاینت‌ها تمام گزینه‌هایش را بخوانند. به دستگاه انتخاب‌شده وابسته است و UUID را داخل فایل دارد. فایل را در چت یا Git نگذارید.

پیش‌فرض‌ها:
- Fragment خاموش؛ هنگام فعال‌کردن، `tlshello`، طول نمونه `100-200` بایت، فاصله نمونه `10-20` میلی‌ثانیه. این‌ها نمونهٔ مستندات‌اند، نه تضمین سازگاری همراه اول.
- Mux خاموش؛ concurrency قابل‌انتخاب ۱ تا ۳۲، پیش‌فرض ۸ در صورت فعال‌سازی.
- بررسی TLS روشن و `allowInsecure=false`؛ fingerprint کروم؛ SNI و Host همان دامنهٔ معتبر سرور.
- پورت SOCKS محلی پیش‌فرض 10818 با bind به `127.0.0.1`. پورت باید با برنامهٔ دیگری تداخل نداشته باشد.
- ترجیح IPv4 اختیاری. DNS سیستم/تنظیمات v2rayN نصب‌شده تغییر نمی‌کند.

خروجی مستقل است و برای اجرا در حالت Custom Config کلاینت یا Xray-core باید نسخه و مسیر واردکردن آن جدا بررسی شود. پروفایل فعال و کارکردهٔ قبلی را جایگزین نکنید؛ ابتدا یک کپی آزمایشی بسازید. ترکیب Mux با Fragment در این نسخه روی شبکهٔ واقعی آزمایش نشده است.

منابع خوانده‌شده در 2026-09-08:
- https://xtls.github.io/en/config/outbounds/freedom.html
- https://xtls.github.io/en/config/transport.html

شبکهٔ فعلی سرور همچنان WebSocket است. XHTTP همچنان پژوهشی/فعال‌نشده است و این انتشار ادعای «بهترین تنظیمات قطعی» ندارد.

## نصب و بازگشت

1. همان شاخهٔ `arena/01a080a2-darvazeh` و همان Volume `/data`، فقط یک replica. main/production دست‌نخورده‌اند.
2. Rebuild آخرین نسخه و بررسی `/api/bootstrap` و «دربارهٔ برنامه»: `0.3.0-preview.1`.
3. دستگاه‌های فعلی باید با نام و لینک قبلی و بدون سقف تازه ظاهر شوند. قبل از تعیین سقف برای کاربر واقعی، یک دستگاه آزمایشی بسازید و نوار/وضعیت آن را بررسی کنید.
4. اگر پایش مشکل داشت، `MONITOR_ENABLED=0` و Restart فقط مسیر دستگاه‌های نامحدود را حفظ می‌کند؛ **دستگاه‌های محدود عمداً بسته می‌مانند**.
5. بازگشت به ایمیج قدیمی ممکن است فیلدهای سهمیه را نادیده بگیرد یا DB نسخه۲ را نشناسد. آن را راه‌حل امن حفظ سهمیه فرض نکنید؛ ابتدا با مدیر دربارهٔ سیاست کاربران محدود و روش بازگردانی بحث کنید. داده‌ها/Volume را خودسرانه حذف نکنید.

## آزمون‌ها و مرز تأیید

- ۳۴ تست Python: سهمیهٔ مشترک هم‌زمان، پایداری بعد از restart/حذف تاریخچه/تعویض کلید، مهاجرت یک‌باره، روز تقویمی، جلوگیری از bypass، قطع حجم و انقضا با سوکت واقعی، سالم‌ماندن دستگاه دیگر، fail-closed خطای DB، رد Early Data در حالت محدود، امنیت و آزمون‌های قبلی.
- peer تست شبکه کنترل‌شده است؛ این تست‌ها جای Xray واقعی یا مسیر Hostim/اپراتور را نمی‌گیرند.
- مرورگر واقعی Chromium: ورود، تب‌ها، مودال ساخت/ویرایش/لغو، progressbar، جست‌وجو، لینک، خروجی JSON، Escape، موبایل/دسکتاپ و نبود overflow صفحه؛ بدون خطای JS و بدون dialog بومی مرورگر. HTML/CSS/JS واقعی با API واقعی حالت نمایشی استفاده شد؛ ردیف ساختگیِ اتصال زنده اضافه نشد.
- jsdom نیز مسیر UI/API و اعتبارسنجی خروجی کلاینت را اجرا کرده است.
- تصویر desktop/modal/mobile توسط ایجنت بررسی شد. موتور Chromium از بستهٔ npm در ابزارهای آزمایش نصب شد؛ کتابخانه‌های بستهٔ al2023 برای اجرا استفاده شدند. این وابستگی‌ها جزو ایمیج تولید نیستند.
- Docker build، تست کانفیگ خروجی با باینری Xray و تونل واقعی Hostim این نسخه هنوز در این محیط تأیید نشده‌اند. پس از استقرار، تست کلاینت واقعی لازم است.
